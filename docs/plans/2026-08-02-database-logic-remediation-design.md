# 数据库与业务逻辑整改设计

> 设计日期：2026-08-02
> 对应审计：`docs/database-business-logic-audit-2026-08-02.md`
> 状态：已确认，待实施

## 目标

修复 MySQL 到 PostgreSQL 重构后暴露的资金事务、支付回调、转账一致性、SQL 方言、表前缀及旧库升级问题，同时保持现有 API 参数和主要业务状态含义不变。

## 范围

本轮覆盖审计报告中的 `DB-01` 至 `DB-09`：

- 转账外部副作用与本地事务一致性。
- 商户余额和资金流水原子更新。
- 支付回调内部数据库错误传播。
- 商户回调重试 SQL。
- PostgreSQL 旧数据库版本升级。
- 随机支付通道兜底。
- 后台 PostgreSQL 不兼容 SQL。
- 自定义数据表前缀。
- `PdoHelper` 错误状态管理。

不在本轮范围内：

- 全项目 Repository 或 ORM 重写。
- 支付插件协议和第三方 SDK 重构。
- 改变现有商户 API 的请求和响应字段。
- 与审计问题无关的安全或界面重构。

## 总体方案

采用“严格数据库错误传播 + 转账状态机 + 版本化迁移 + PostgreSQL 兼容测试”的方案。

所有资金写操作必须满足以下原则：

1. 返回成功代表相关订单、余额和流水已经提交。
2. 任意数据库写入失败必须立即停止当前业务流程。
3. 事务失败必须回滚到调用前的事务深度。
4. 外部平台调用不能被数据库长事务包围。
5. 外部结果不确定时必须保留可查询、可对账的本地记录。

## 余额事务设计

### `changeUserMoney()`

该函数作为独立资金操作入口，负责完整事务边界：

1. 开启事务或嵌套保存点。
2. 使用 `SELECT ... FOR UPDATE` 锁定商户。
3. 确认商户存在且旧余额为有效数值。
4. 计算新余额。
5. 更新商户余额，并要求恰好影响一行。
6. 插入资金流水，并要求插入成功。
7. 提交当前事务层级。
8. 任一步失败时回滚到进入函数前的事务深度并抛出异常。

金额小于等于零继续作为无操作处理，但返回明确成功值，避免调用方把无操作误认为数据库失败。

### `changeUserMoney2()`

该函数只允许在调用方已经持有用户行锁并开启事务时使用。它不再自行提交事务，但必须：

- 验证旧余额。
- 验证余额更新影响一行。
- 验证资金流水插入成功。
- 失败时抛出异常，由外层事务统一回滚。

## 转账一致性设计

当前转账流程在数据库事务中调用外部平台，存在外部成功、本地提交失败的风险。整改后拆分成三个阶段。

### 阶段一：本地预留

在短事务中执行：

1. 通过 `out_biz_no + uid` 检查幂等性。
2. 锁定商户并重新计算可转余额。
3. 插入 `pre_transfer` 记录，状态使用现有 `status=0`（处理中）。
4. 在 `result` 中记录等待提交到外部平台的阶段信息。
5. 原子扣除余额并写资金流水。
6. 提交事务。

完成后才允许调用外部平台。这样即使 PHP 进程随后退出，本地仍存在唯一转账记录，且重复请求不会再次扣款。

### 阶段二：外部提交

在数据库事务之外调用支付平台，并始终使用已经持久化的 `biz_no/out_biz_no`。

- 外部明确成功：进入本地完成阶段。
- 外部明确失败：进入本地失败和退款阶段。
- 超时、网络异常或响应无法判断：保留 `status=0`，等待主动查询。

### 阶段三：本地完成

使用新的短事务锁定转账记录并更新结果：

- 成功：更新为 `status=1` 或平台返回的处理中状态，并保存平台单号。
- 明确失败：更新为 `status=2`，在同一事务中退回余额并写退款流水。
- 本地更新失败：预留记录继续保持 `status=0`，后续通过转账查询按 `biz_no` 恢复。

不新增会破坏现有页面判断的主状态值。`status=0` 继续表示处理中，也承担待对账含义；详细阶段和错误原因写入现有 `result` 字段。

红包转账采用相同的本地预留和严格事务原则，但保留现有 `status=4` 待领取语义。

## 支付回调设计

支付回调继续使用订单行锁和条件状态认领，但加强以下约束：

- 所有订单字段更新必须检查数据库返回值。
- 全局 `processOrder()` 内的余额、流水、返佣和分账写入失败必须抛出异常。
- 回调事务捕获异常后回滚到进入前的事务深度。
- 错误日志记录订单号、处理阶段和第一条数据库错误。
- 只有完整提交后才能向支付插件返回业务成功。

不改变现有重复回调幂等规则。

## PostgreSQL SQL 兼容设计

对明确、有限的方言差异优先修改业务 SQL，使语义直接可读：

- `TO_DAYS()` 改为时间范围比较。
- `ORDER BY RAND()` 根据驱动选择 `RAND()` 或 `RANDOM()`。
- `NOW()-INTERVAL N DAY` 改为转换器已支持的 `DATE_SUB()`，或绑定计算后的时间值。
- 移除由唯一键条件保证范围的 `UPDATE ... LIMIT 1`。

只有多处重复且语义稳定的表达式才加入 `PdoHelper::dealSql()`，避免使用复杂正则模拟完整 SQL 解析器。

业务代码必须区分“查询结果为空”和“查询执行失败”。定时任务遇到查询失败时应记录错误并终止当前轮次，不能静默当作没有任务。

## 表前缀设计

运行时代码统一使用 `pre_` 逻辑表前缀，让 `PdoHelper` 替换为实际前缀。初始化和升级脚本使用已经验证的 `$prefix` 构造表名。

所有新增测试至少覆盖一次非默认前缀，防止再次硬编码 `pay_`。

## PostgreSQL 升级设计

旧库升级改为显式、幂等、逐版本执行：

1. 读取当前版本。
2. 按版本顺序执行 PostgreSQL 专用迁移步骤。
3. 每个步骤使用结构检查和 `IF NOT EXISTS` 保证重复执行安全。
4. 当前版本的全部表、字段、索引和约束创建成功后才更新版本号。
5. 任一步失败时回滚该版本迁移，不允许跳写最终版本。

迁移验证同时比较：

- 从空数据库执行完整安装后的结构。
- 从旧版本数据库执行升级后的结构。

两者关键业务表结构必须一致。

## `PdoHelper` 错误管理设计

每次 `exec()` 和 `query()` 开始时清空上一条错误。失败时保存当前 PDO 错误；事务开始、提交、回滚和保存点操作失败时也保存对应错误。

`transaction()` 必须检查提交和回滚结果，不能在提交失败后返回业务成功值。

## 测试策略

所有修复遵循测试先行：先增加能稳定复现当前错误的测试，确认失败后再修改生产代码。

重点测试包括：

- 商户不存在时余额操作失败且不产生流水。
- 流水插入失败时余额不变。
- 嵌套事务失败后恢复到原事务深度。
- 转账预留只扣款一次。
- 外部成功、本地完成失败时保留可对账记录。
- 外部明确失败时余额只退回一次。
- 支付回调任意中间写入失败时完整回滚。
- 回调重试、随机通道、后台筛选和批量更新在 PostgreSQL 上执行成功。
- 非默认数据库前缀可运行相关查询。
- 旧库升级后关键结构与全新安装一致。
- 成功查询不会继续暴露上一条 SQL 错误。

## 发布与恢复

- 数据库迁移必须在应用代码使用新字段之前完成。
- 迁移保持向前兼容，不删除现有字段或状态。
- 转账流程上线后重点观察 `status=0` 的滞留数量、事务错误日志和重复 `out_biz_no`。
- 已经外部成功但本地状态异常的历史订单通过平台查询接口人工或批量恢复，不直接修改余额。

## 验收标准

- 资金操作不存在余额成功、流水失败或订单成功、余额失败的半完成状态。
- 外部转账结果不确定时不会重复扣款或直接发起新的业务单号。
- 首次商户通知失败后能按照既定间隔重试。
- PostgreSQL 下通道兜底、后台筛选和批量状态修改正常执行。
- 非默认表前缀不访问 `pay_` 硬编码表。
- 旧库升级和全新安装的关键数据库结构一致。
- 新增回归测试及现有数据库、支付回调测试全部通过。
