## PostgreSQL 迁移验证

`PostgresSchemaUpgradeTest.php` 验证了：

- 从最小旧结构和版本 `2043` 升级到 `2056`。
- 补齐转账、退款、分账、子通道和子订单等业务表。
- 补齐订单、商户、通道、插件等关键字段和索引。
- 修正插件、密码和消息配置字段类型。
- 补齐支付类型 6 和 7。
- 将历史 `user.wxid` 数据迁移到 `wx_uid`，并扩容旧版 `ip`、`buyer` 等字段。
- 重复运行迁移保持幂等。
- 任意结构 SQL 失败时整体回滚，版本仍保持 `2043`。
- 即使历史错误升级已经把版本写成 `2056`，容器启动仍会执行幂等结构核对。
- 当前结构完整时轻量探针返回无需协调，不会在每次容器启动时执行 `ALTER TYPE`。

## Docker 构建与初始化

使用独立项目名和空数据卷启动当前分支，避免影响现有 `8090` 环境：

```powershell
$env:APP_PORT='8091'
docker compose -p epay-remediation --env-file G:\epay\.env `
  -f G:\epay\.worktrees\database-logic-remediation\docker-compose.yml `
  up -d --build
```

验证结果：

```text
epay-remediation-app-1  healthy
epay-remediation-db-1   healthy
app log: PostgreSQL schema initialized
container-local HTTP status: 200
```

宿主机使用 `http://127.0.0.1:8091/` 且没有生产域名 Host 时返回 `404`，但容器内健康检查返回 `200`。这是当前站点 Host/入口路由行为，不是数据库初始化或容器健康故障。

## 部署注意事项

1. 生产更新前完整备份 PostgreSQL 数据库和上传文件。
2. 先在生产数据副本上运行一次相同镜像，确认日志出现升级成功且版本为 `2056`。
3. 升级失败时不要手工修改 `pre_config.version`，应保留原版本并根据首条 SQL 错误处理。
4. 部署后检查支付回调、商户通知重试、订单查询、余额流水和转账查询。
5. 使用支付平台沙箱或一笔小额实付完成端到端回调验收。
