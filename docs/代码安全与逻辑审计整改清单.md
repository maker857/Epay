## 整改项目

### - [x] SEC-01 支付回调幂等性与事务一致性

**严重程度：严重**

**问题说明**

支付回调先根据旧订单状态判断，再执行没有状态条件的 `UPDATE status=1`。在 PostgreSQL 下，并发的重复通知可能都被认为更新成功，随后重复执行余额入账、返佣、分账和通知。订单状态更新与后续资金操作也没有放在同一完整事务中，中途失败可能产生已支付但未完整入账的订单。

**相关位置**

- `includes/lib/Payment.php:344`
- `includes/lib/Payment.php:347`
- `includes/functions.php:607`
- `includes/functions.php:792`

**整改要求**

- 使用带旧状态条件的原子更新，例如仅允许 `status IN (0, 4)` 的订单进入成功状态。
- 只有成功抢占订单处理权的请求才能继续入账。
- 设计完整事务边界，避免订单状态、余额流水、返佣和分账只完成一部分。
- 为重复通知、并发通知和中途异常添加回归测试。

**验收标准**

- 同一订单并发发送多次成功通知，只产生一次余额流水和一次返佣/分账。
- 任一步骤失败后不会留下无法恢复的半完成状态。
- 重复通知能够返回支付平台期望的成功响应，但不会再次入账。

**整改记录**

- 修复日期：2026-07-31
- 修复提交：待提交（本次修复）

### - [ ] SEC-02 PostgreSQL SQL 注入风险

**严重程度：严重**

**问题说明**

项目大量使用 `daddslashes()` 后拼接 SQL。该函数底层只是 `addslashes()`，不能替代 PDO 参数绑定，尤其不适用于 PostgreSQL 的字符串语法。公共支付入口、查询 API、商户后台和管理员后台均存在类似代码。

**相关位置**

- `includes/functions.php:217`
- `submit2.php:10`
- `cashier.php:9`
- `getshop.php:23`
- `api.php:57`
- `admin/ajax_user.php:19`
- `user/ajax2.php:940`

**整改要求**

- 所有数据值改用 PDO 参数绑定。
- 表名、字段名、排序字段和排序方向不能使用参数绑定的部分，必须使用固定白名单。
- 禁止将 `$_GET`、`$_POST`、`$_REQUEST` 或未经验证的变量直接拼接进 SQL。
- 添加针对单引号、注释符、排序字段和模糊搜索的注入测试。

**验收标准**

- 代码扫描不再发现用户输入直接拼接 SQL 的路径。
- 公共入口和后台搜索接口的注入测试全部通过。
- 合法查询、分页、排序和模糊搜索行为保持不变。

### - [ ] SEC-03 恢复 HTTPS 证书校验

**严重程度：严重**

**问题说明**

通用 cURL 方法关闭了服务端证书和主机名校验。支付接口、OAuth、短信、证书下载及其他第三方请求都可能遭受中间人攻击。

**相关位置**

- `includes/functions.php:33`
- `includes/functions.php:34`
- `includes/functions.php:46`
- `includes/functions.php:47`

**整改要求**

- 开启 `CURLOPT_SSL_VERIFYPEER` 和 `CURLOPT_SSL_VERIFYHOST`。
- 使用系统 CA 证书包，容器内明确安装 `ca-certificates`。
- 对确实需要自定义 CA 的通道提供单独、受控的 CA 文件配置。
- 禁止通过生产配置全局关闭 TLS 校验。

**验收标准**

- 有效 HTTPS 地址请求成功。
- 自签名证书、过期证书和主机名不匹配的请求失败。
- 主要支付插件的下单、查询、退款和回调验证通过。

### - [ ] SEC-04 修复 TOTP 登录流程

**严重程度：高**

**问题说明**

管理员 TOTP 接口只校验六位动态口令，没有确认当前会话已经通过管理员用户名和密码，也没有独立的失败次数限制。TOTP 因此可能被当作单独登录凭证使用。

**相关位置**

- `admin/login.php:67`
- `admin/login.php:75`
- `admin/login.php:83`

**整改要求**

- 密码验证成功后生成短期、一次性的 TOTP 登录挑战。
- TOTP 接口必须验证挑战存在、未过期且尚未使用。
- 增加基于账号和可信客户端 IP 的失败次数限制。
- 登录成功后销毁挑战，并重新生成会话标识。

**验收标准**

- 未先通过密码验证时，正确 TOTP 也不能登录。
- 挑战过期或重复使用时登录失败。
- TOTP 连续失败达到阈值后受到限制。

### - [ ] SEC-05 升级密码存储算法

**严重程度：高**

**问题说明**

商户密码使用固定结构的快速 MD5，管理员密码以明文配置值进行比较。数据库泄露后，密码容易被离线破解或直接使用。

**相关位置**

- `includes/functions.php:448`
- `user/ajax.php:71`
- `user/ajax.php:340`
- `admin/login.php:37`
- `admin/set.php:220`

**整改要求**

- 使用 `password_hash()` 的 Argon2id 或 bcrypt。
- 使用 `password_verify()` 验证密码。
- 保留旧密码兼容验证，并在用户成功登录后自动升级哈希。
- 管理员密码不再以明文形式长期存储。
- 增加密码修改后旧 Cookie/Token 失效测试。

**验收标准**

- 新密码只以强哈希形式保存。
- 旧账号仍可登录，并在首次成功登录后完成哈希升级。
- 数据库中不能直接读取管理员明文密码。

### - [ ] SEC-08 完善 Cookie 与 CSRF 防护

**严重程度：中**

**问题说明**

管理员和商户登录 Cookie 缺少完整的 `Secure`、`SameSite`、路径和生命周期策略。部分敏感操作只检查 Referer，另有修改操作使用 GET 请求。

**相关位置**

- `admin/login.php:50`
- `admin/login.php:86`
- `user/ajax.php:105`
- `admin/pay_plugin.php:13`
- `admin/set_totp.php:4`
- `includes/functions.php:923`

**整改要求**

- 登录 Cookie 设置 `HttpOnly`、`Secure`、`SameSite=Lax` 或更严格策略。
- 所有修改操作使用 POST/PUT/DELETE，不使用 GET。
- 使用服务端生成的随机 CSRF Token，不把 Referer 作为唯一防护。
- 登录后和权限变化后重新生成会话标识。

**验收标准**

- 缺少或伪造 CSRF Token 的修改请求返回 403。
- GET 请求不能刷新插件、删除记录或修改状态。
- 浏览器中 Cookie 属性符合预期。

### - [ ] SEC-09 建立可信反向代理 IP 策略

**严重程度：中**

**问题说明**

客户端 IP 获取逻辑无条件信任 `X-Forwarded-For`、`CF-Connecting-IP` 和 `X-Real-IP`。攻击者可能伪造 IP，绕过登录限制、黑名单和风控。

**相关位置**

- `includes/functions.php:87`
- `includes/functions.php:89`
- `includes/functions.php:100`

**整改要求**

- 默认使用 `REMOTE_ADDR`。
- 仅当直连来源属于配置的可信反向代理时解析代理请求头。
- aaPanel/Nginx 覆盖外部传入的代理请求头。
- 使用 Cloudflare 时只信任其官方 IP 网段，并建立更新机制。

**验收标准**

- 直接伪造代理请求头不能改变系统识别的客户端 IP。
- 经可信 aaPanel/Nginx 代理时能够获得真实客户端 IP。
- 登录限流和 IP 黑名单使用同一可信 IP 结果。

### - [ ] SEC-12 加固依赖管理与容器权限

**严重程度：低**

**问题说明**

Composer 依赖没有锁文件，构建结果难以复现。容器内整个项目目录归 Web 用户所有，Web 进程能够修改 PHP 和插件代码。

**相关位置**

- `includes/composer.json`
- `Dockerfile:22`
- `docker-compose.yml`

**整改要求**

- 生成并提交 `composer.lock`，在构建时使用锁定版本安装依赖。
- 执行依赖漏洞扫描并记录结果。
- 应用源码设为只读，仅对缓存、上传和证书目录授予最小写权限。
- 评估增加 `read_only`、`no-new-privileges`、`cap_drop` 和临时目录挂载。
- 增加 CSP、`X-Content-Type-Options`、`Referrer-Policy`、`Permissions-Policy` 等响应头。

**验收标准**

- 相同提交能够构建出一致的依赖版本。
- Web 用户不能修改 PHP 源码和插件文件。
- 应用所需上传、缓存和运行时写入功能保持正常。
- 容器和依赖扫描没有未处理的高危问题。
